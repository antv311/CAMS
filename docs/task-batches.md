# Task batches

Both batch endpoints require an account bearer token and accept 1..100 items.
An invalid item rejects the entire request: no task changes, dependency edges,
audit events, task counters, or task notifications from that request survive.
The server commits task records and audit events in one SQLite transaction.
Notifications and worker wakes are attempted after commit; delivery failures
are logged and do not turn a committed request into a failure response.

## Create a backlog

`POST /v1/tasks/batch` takes a `tasks` array. Each item accepts the same fields
as `POST /v1/tasks`, plus an optional `key` unique within the request. A key is
1..64 ASCII letters, digits, underscores, or hyphens. IDs are generated by the
hub. Use `$key` in `blocked_by` or `parent_task_id` to reference another item,
including one appearing later in the array. Ordinary task IDs reference
existing tasks. Missing references, self dependencies, dependency cycles and
parent cycles reject the request.

```json
{
  "tasks": [
    {
      "key": "ui",
      "channel": "#app-s4",
      "title": "Connect the UI",
      "assignee": "frontend",
      "blocked_by": ["$api"]
    },
    {
      "key": "api",
      "channel": "#app-s4",
      "title": "Build the API",
      "assignee": "backend",
      "priority": "high",
      "timeout_seconds": 1800
    }
  ]
}
```

Success is HTTP 201 with `{"ok":true,"tasks":[...],"task_ids":{"ui":"task_...","api":"task_..."}}`.
Tasks are returned in input order. Only items with a key appear in `task_ids`.
The usual project/sprint resolution, parent inheritance, project repository,
account membership, reviewer, priority and timeout validation apply. Creation
requires a `pm` token scope, just like single-task creation; account permissions
are checked for every item, including delegation to other people.

## Move tasks together

`POST /v1/tasks/bulk-status` takes an `updates` array. Each item requires a
distinct, nonblank `task_id` and `status`; it may also include `note`, `branch`,
`report_body`, `report_id`, and `commit`, with the same meanings as the
single-task status endpoint. Unknown update fields are rejected.

```json
{
  "updates": [
    {"task_id":"task_api", "status":"merged", "note":"Reviewed and accepted"},
    {"task_id":"task_ui", "status":"in_progress"}
  ]
}
```

Success is HTTP 200 with `{"ok":true,"tasks":[...]}` in input order. Updates
are evaluated in request order inside one transaction. A blocker can be merged
before a dependent starts in the same batch, provided the caller has permission
for both transitions. Reversing those entries fails and rolls back the batch.
Duplicate task IDs are rejected; a batch cannot skip workflow phases by listing
the same task repeatedly. Sending a task to `review` still requires prior
`testing` and a nonblank test report. Peer consensus and revision checks apply.

The token needs `write` for batches containing only `in_progress`, `testing`,
and `review` targets. If any target needs `pm` in the single-task API, the whole
request needs `pm`. Token scope does not grant project permissions: an assignee,
named reviewer, or project manager can only perform their usual transitions.
Tasks with unresolved dependencies or expired execution cannot bypass those
guards through a batch.

Cancelling a parent cascades to descendants using the ordinary workflow rules.
If a descendant is also explicitly listed in the batch, the
request fails in either order; submit the ancestor alone. This prevents stale explicit changes
and contradictory worker notifications. Completed descendants remain preserved.

Validation failures use HTTP 400 and an `error` message, usually including the
zero-based `tasks[index]` or `updates[index]` and its cause. Missing or invalid
credentials use 401, insufficient token scope uses 403, and malformed JSON or
field types use Axum's normal 4xx responses. These are ordinary POST endpoints;
creation does not provide an idempotency key.

## Python SDK

```python
created = hub.create_task_batch([
    {"key": "a", "channel": "#app-s4", "title": "First", "assignee": "dev"},
    {"key": "b", "channel": "#app-s4", "title": "Next", "blocked_by": ["$a"]},
])
tasks = hub.bulk_task_status([
    {"task_id": created["task_ids"]["a"], "status": "testing"},
])
```
